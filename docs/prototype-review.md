**Insurance claims portal: prototype review and completion proposal**

Reviewed on 3 October 2026. Scope: the current portal, with **Motor and Burglary only**, agent-led policyholder invitations, and manual portal workflows while insurer integration remains deferred.

The project has a useful foundation, but the intended journey is incomplete. A policyholder cannot currently follow a coherent agent invitation through account activation, immediate incident reporting, evidence submission, and a clear response. The priority should be to complete that journey and correct access rules before expanding the product.

This is a review, not an implementation. Application code was left unchanged. No commits, migrations, account creation, claim submission, email dispatch, or storage uploads were performed.

**What is already implemented**

- Separate six-step Motor and Burglary forms, validation feedback, categorized file selection, and a burglary loss inventory with a replacement-value total.
- Four roles: `user`, `agent`, `head_agent`, and `admin`, with separate dashboards and a permission map.
- Organizations, staff memberships, an organization switcher, policy records, claim records, and separate detail records for the two products.
- A manager assignment queue, agent claim assessment views, status changes, notes, and editable progress steps.
- Stored notifications and an attachment-view endpoint that checks ownership or staff access before issuing a five-minute signed URL.
- Sign-in, password reset, email-verification screens, and profile/password settings.

These are worth retaining. Completing their behavior will deliver more value than another visual redesign.

**Confirmed defects and gaps, in priority order**

1. **Policyholder onboarding does not implement the invitation journey.** The agent action directly inserts a user and policy. It creates no invitation, sends no email, and creates no password credential. The staff invitation action only accepts `admin`, `head_agent`, and `agent`; its permission is restricted to administrators. Newly inserted policyholders also collide with ordinary sign-up: the installed Better Auth sign-up handler rejects an existing email. Its password-reset handler can create a missing credential, but the portal never presents that as an account-activation journey. Phone is required and then discarded; the ID selected in the onboarding UI is never sent to the action. Existing accounts are reused by email without checking their role or whether their organization matches the new policy. [Onboarding action](C:/Users/ADMIN/Desktop/insurance-portal/app/actions/agent/onboard-policyholder.ts:80), [staff invitations](C:/Users/ADMIN/Desktop/insurance-portal/app/actions/admin/manage-agents.ts:13), [onboarding UI](C:/Users/ADMIN/Desktop/insurance-portal/components/dashboard/agent/onboard-policyholder.tsx:44).

   **Recommendation:** keep pending invite/enrollment information separate from login identities. Let the authentication system create credentials, then associate the verified account with the authorized enrollment. An existing account should sign in and explicitly accept the invitation. Persist contact information; either implement ID storage with a stated purpose or remove that field from onboarding.

2. **Staff privileges can be granted without verified email ownership.** Public sign-up is enabled without an invitation requirement or required email verification. The dashboard layout finds a pending invitation by the signed-in email and automatically accepts it. The acceptance action also allows a token plus email to update an existing user's global role without requiring an authenticated, verified account. In combination, someone registering an unclaimed invited staff email could receive its staff role through the layout fallback without possessing the invitation link. This is a source-confirmed authorization path; no account takeover was attempted. [Auth configuration](C:/Users/ADMIN/Desktop/insurance-portal/lib/auth.ts:36), [automatic acceptance](C:/Users/ADMIN/Desktop/insurance-portal/app/(pages)/layout.tsx:22), [token acceptance](C:/Users/ADMIN/Desktop/insurance-portal/app/actions/admin/manage-agents.ts:97).

   **Recommendation:** require a valid invitation on the server for portal enrollment, authenticate and verify the intended identity, and accept that specific invitation explicitly. Do not grant roles from an email-only lookup or change account roles while rendering a page. Better Auth exposes an explicit email-verification requirement; adding a verification screen alone does not enforce it. [Better Auth documentation](https://better-auth.com/docs/authentication/email-password).

3. **Claim authorization is inconsistent across server actions.** `getClaimDetails` checks organization access and rejects unassigned agents, but does not reject a policyholder reading another policyholder's claim in the same organization. `getClaimTimeline` relies on that function. The staff progress reader similarly allows a policyholder with organization access to read another claim's progress. Both submission actions check ownership only for the `user` role; agents and head agents can submit against a policy ID without an organization check. Initial assignment places `requireOrganizationAccess` after a return inside the missing-claim branch, making that check unreachable. Upload authorization permits any staff member in the organization, while viewing attachments requires agent assignment. [Claim reader](C:/Users/ADMIN/Desktop/insurance-portal/app/actions/agent/manage-claims.ts:56), [progress reader](C:/Users/ADMIN/Desktop/insurance-portal/app/actions/agent/progress-steps.ts:12), [submission](C:/Users/ADMIN/Desktop/insurance-portal/app/actions/user/submit-claim.ts:114), [assignment](C:/Users/ADMIN/Desktop/insurance-portal/app/actions/head-agent/manage-claims.ts:129), [upload route](C:/Users/ADMIN/Desktop/insurance-portal/app/api/upload/route.ts:55).

   **Recommendation:** use one claim-access policy across reads, writes, uploads, and downloads: policyholder ownership, assigned-agent access, organization-manager access, and explicit platform-admin access. Assisted filing must verify the customer's policy and the staff member's organization, and record who filed it. Add negative authorization tests. This follows OWASP's guidance to validate access to the specific resource on every request. [OWASP authorization guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html).

4. **A failed upload can leave a saved claim and produce duplicates on retry.** The form first creates a claim, detail records, and progress steps, then uploads documents one at a time. If an upload fails, the user sees a generic error without the saved claim reference. Pressing Submit again creates another claim. The database inserts are separate, so later failures can also leave an incomplete claim. Claim references use a random five-digit number with no collision retry. [Motor submission UI](C:/Users/ADMIN/Desktop/insurance-portal/components/claims/motor-claim-form.tsx:256), [document upload loop](C:/Users/ADMIN/Desktop/insurance-portal/lib/upload-claim-documents.ts:9), [claim creation](C:/Users/ADMIN/Desktop/insurance-portal/app/actions/user/submit-claim.ts:149).

   **Recommendation:** create or resume one draft/report ID, make final submission idempotent, and preserve that ID through every retry. Save related database records atomically using a transaction mechanism supported by the chosen driver. Treat external storage separately: track each upload, retry failed files, reconcile unfinished uploads, and show “Report received; 2 documents still need uploading” when appropriate. The reference should survive a refresh and network retry.

5. **The forms conflict with immediate incident reporting.** Motor requires police station, O.B. number, reporting officer, and all six document categories, including a police abstract and scene photos. Burglary requires a police abstract, proof of purchase, and entry photos. Receipt alternatives are advertised, but purchase receipts remain required, so bank statements do not actually replace them. Neither flow can record a first notification while those details are unavailable. [Motor document requirements](C:/Users/ADMIN/Desktop/insurance-portal/components/claims/motor-claim-form.tsx:69), [Burglary document requirements](C:/Users/ADMIN/Desktop/insurance-portal/components/claims/burglary-claim-form.tsx:72), [form schemas](C:/Users/ADMIN/Desktop/insurance-portal/lib/schemas/claim-forms.ts:11).

   **Recommendation:** separate “Report the incident” from “Complete supporting information.” Collect enough to identify the policy, incident, contact person, and broad loss; issue an immediate receipt. Track outstanding evidence explicitly and allow “Not available yet,” with a reason where useful. Keep the distinction between a received incident report and a package ready for review.

6. **Burglary is missing the date/time of the incident; Motor lacks incident-specific branching.** Burglary stores when police were notified, but has no incident or discovery date/time in the form or details table. Motor advertises theft and vehicle damage but always asks accident-oriented questions such as driver, speed, weather, and scene photos. A parked-car loss should not force invented driving information. [Burglary details](C:/Users/ADMIN/Desktop/insurance-portal/db/schema/burglary-claim-details.ts:17), [Motor steps](C:/Users/ADMIN/Desktop/insurance-portal/components/claims/motor-claim-form.tsx:56).

   **Recommendation:** add incident timing to Burglary, including discovery time and an approximate range if the event time is unknown. Within Motor, ask the incident type first and conditionally show accident, theft, or other damage questions. These are branches within the existing policy, not new policy products.

7. **Server validation accepts impossible data and differs from client validation.** Both server schemas mostly test whether text is nonempty. Isolated execution of the actual schema expressions accepted a Motor payload containing a negative mileage and experience, `not-a-date`, `99:99`, and `maybe` as drivable. Burglary accepted invalid dates, nonnumeric/negative values, and contradictory alarm answers. The client schemas are separate and stricter in some text-length rules. Document requirements are only checked in the browser. [Server schemas](C:/Users/ADMIN/Desktop/insurance-portal/app/actions/user/submit-claim.ts:75), [client schemas](C:/Users/ADMIN/Desktop/insurance-portal/lib/schemas/claim-forms.ts:11).

   **Recommendation:** share schemas and conditional rules. Trim text, bound lengths, validate date/time values and chronology, use explicit answer enums, and represent unknown values deliberately. Validate positive money with a decimal-safe representation, rather than accepting arbitrary strings or treating parse errors as zero. Enforce completeness requirements on the server when advancing a report to the relevant stage.

8. **Selected documents lose their category and are not consistently validated.** The upload helper flattens the category map, and the attachment table has no category or loss-item association. Burglary accepts `.xlsx` and `.csv` in the picker, but the API rejects them. The picker advertises broad image/video support while the server accepts a narrower list, and drag-and-drop does not enforce the picker filter. A single-file category can accumulate several files. The attachment-record action trusts caller-supplied object metadata and does not verify the stored object; the presigned-upload path does not bind a maximum size. [Upload helper](C:/Users/ADMIN/Desktop/insurance-portal/lib/upload-claim-documents.ts:9), [attachment schema](C:/Users/ADMIN/Desktop/insurance-portal/db/schema/claim-attachments.ts:11), [picker](C:/Users/ADMIN/Desktop/insurance-portal/components/claims/document-uploader.tsx:69), [attachment recording](C:/Users/ADMIN/Desktop/insurance-portal/app/actions/user/submit-claim.ts:372).

   **Recommendation:** keep category, associated loss item, uploader, upload state, and review state. Make picker, drag-and-drop, API, and storage limits agree. Validate files before submission, bind uploads to an authorized claim, verify object metadata before recording success, and check content rather than trusting the supplied MIME type. Define per-file and total limits. Before using real sensitive documents, add a controlled scan/quarantine process. [OWASP file-upload guidance](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html).

9. **Important dashboard actions appear complete but do not work.** Document Vault Upload and Download buttons have no handlers or links. The reassignment dialog declares success using local state; the head-agent page supplies no `onReassign` handler, and the existing `reassignClaim` server action is not connected to it. Forms and onboarding components also contain success fallbacks when policy/organization IDs are absent, which can falsely imply persistence if they enter an application path. [Document Vault](C:/Users/ADMIN/Desktop/insurance-portal/components/dashboard/user/document-vault.tsx:59), [reassignment dialog](C:/Users/ADMIN/Desktop/insurance-portal/components/dashboard/head-agent/reassign-agent-dialog.tsx:38), [manager page](C:/Users/ADMIN/Desktop/insurance-portal/app/(pages)/dashboard/head-agent/head-agent-dashboard-client.tsx:119), [onboarding fallback](C:/Users/ADMIN/Desktop/insurance-portal/components/dashboard/agent/onboard-policyholder.tsx:66).

   **Recommendation:** wire every visible action to persisted behavior and show success only after it succeeds. Use claim IDs, agent IDs, and organization IDs. Keep demonstration behavior behind an explicit demo mode; missing identifiers should produce a useful setup message in the normal application.

10. **Notifications and outcomes do not reach the policyholder clearly.** Status changes and notes create notification records, but `getMyNotifications` is unused and no notification inbox/read action is wired. The main user tracker receives progress steps but not claim status, so it cannot clearly represent rejection or settlement. “Next Steps” always reports no action required. The separate claims list does show status, but the primary dashboard needs the actual status, outcome reason, and requested action. All non-settled claims appear to await approval in the settlement card, while settled claims display “Paid” and KES 0 without payment evidence. [Notification reader](C:/Users/ADMIN/Desktop/insurance-portal/app/actions/user/my-claims.ts:150), [user dashboard](C:/Users/ADMIN/Desktop/insurance-portal/app/(pages)/dashboard/user/user-dashboard-client.tsx:215), [settlement mapping](C:/Users/ADMIN/Desktop/insurance-portal/app/(pages)/dashboard/user/user-dashboard-client.tsx:320).

    **Recommendation:** show the authoritative status, a plain-language explanation, last update, agent contact, and next action. Add a notification inbox with claim links and read state, plus a public claim timeline. Distinguish internal notes from policyholder messages. Store rejection/closure reasons as structured outcome data. Settlement should remain unavailable or explicitly simulated until an amount/reference/evidence is recorded; a claim status alone should not assert a payment occurred.

11. **Claim statuses and progress can contradict each other; deletion destroys history.** An assigned agent can set any available status without a transition or prerequisite check. Custom progress steps can be marked, reopened, or removed independently. A policyholder can permanently delete any owned claim except approved/settled, including an assigned, investigated, or rejected claim. Deletion removes notes and attachment metadata in separate operations, while stored files remain in object storage. [Status updates](C:/Users/ADMIN/Desktop/insurance-portal/app/actions/agent/manage-claims.ts:177), [progress actions](C:/Users/ADMIN/Desktop/insurance-portal/app/actions/agent/progress-steps.ts:95), [claim deletion](C:/Users/ADMIN/Desktop/insurance-portal/app/actions/user/my-claims.ts:202).

    **Recommendation:** define allowed transitions and who can perform them, with manager confirmation for outcomes and an auditable reason for reopening. Derive primary progress milestones from events; retain custom tasks as supporting work. Allow deletion of unsubmitted drafts and a recorded withdrawal request for submitted claims. Retain the original submission and history, with an explicit file-retention/cleanup policy.

12. **Management metrics and organization handling can mislead users.** The bottleneck page passes claim counts into `avgDays`; the chart describes them as average duration and sums them as days. Workload counts include settled/rejected claims, and the “latest claim” query lacks the active-organization filter. Client dashboards filter by organization name and retain claim/detail state in `useState` across refreshed props; switching organization or rapidly selecting claims can leave a displayed selection paired with stale details. [Metric mapping](C:/Users/ADMIN/Desktop/insurance-portal/app/(pages)/dashboard/head-agent/head-agent-dashboard-client.tsx:85), [workload queries](C:/Users/ADMIN/Desktop/insurance-portal/app/actions/head-agent/manage-claims.ts:76), [agent client state](C:/Users/ADMIN/Desktop/insurance-portal/app/(pages)/dashboard/agent/agent-dashboard-client.tsx:72), [organization refresh](C:/Users/ADMIN/Desktop/insurance-portal/lib/org-context.tsx:38).

    **Recommendation:** show “Claims by stage” until actual stage timestamps support elapsed-time metrics. Exclude closed claims from active workload. Scope every query by organization ID, including summaries. Reset or key selected-claim state by organization and claim ID, and prevent earlier requests from overwriting the latest selection. Show a loading state while details change.

13. **Policy data is too thin for the verification language shown.** A policy only stores number, type, owner, organization, and creation time. There are no coverage dates, active/expired state, insured vehicle/premises, or coverage summary, yet screens call policies active and seeded progress promises verification of coverage dates and deductibles. The uniqueness rule also permits only one policy per type per account across all organizations, while onboarding can reuse an account from another organization. [Policy schema](C:/Users/ADMIN/Desktop/insurance-portal/db/schema/policies.ts:6), [default milestones](C:/Users/ADMIN/Desktop/insurance-portal/app/actions/user/submit-claim.ts:58).

    **Recommendation:** retain only Motor and Burglary, but add a minimal manual/demo policy profile: insurer reference, dates, status, insured asset/address, and a concise coverage summary. Do not present generated prototype references as proof of an insurer-issued policy. For the first prototype, one organization per policyholder and one policy of each type is a reasonable boundary; enforce it consistently. If broader membership is wanted later, model it explicitly rather than silently attaching another organization's policy to an existing identity.

14. **Invitation recovery and account settings need completion.** Invitations expire after seven days, but pending-duplicate detection ignores expiry; an expired invitation can block a replacement. There is no resend, revoke, or email-failure recovery action. Invalid invitation links display an ordinary sign-up form, and the invitation is checked only after account creation. Existing users cannot explicitly accept another staff invitation through the sign-up route because authenticated users are redirected away. Email is configured for Mailtrap sandbox with a placeholder sender; auth email callbacks ignore the returned send-failure result. The settings UI calls `changeEmail`, but that capability is not enabled in the auth configuration and the installed library rejects it. [Invitation creation](C:/Users/ADMIN/Desktop/insurance-portal/app/actions/admin/manage-agents.ts:29), [signup handling](C:/Users/ADMIN/Desktop/insurance-portal/app/sign-up/page.tsx:203), [mail configuration](C:/Users/ADMIN/Desktop/insurance-portal/lib/email.ts:5), [email settings](C:/Users/ADMIN/Desktop/insurance-portal/app/(pages)/settings/settings-form.tsx:59).

    **Recommendation:** validate the invitation before showing enrollment, support signed-in acceptance, compute expiry accurately, and offer resend/revoke/retry with a delivery state. Rotate the token on resend and consume it once atomically. Hash stored invitation tokens. Keep staff and policyholder invitations as distinct purposes. Use an explicit sandbox/live email selector with visible development delivery evidence; surface failures without claiming delivery. Enable a secure email-change flow or remove that action until implemented.

**Recommended roles: keep four**

| Display name | Existing role | Responsibility and scope |
| --- | --- | --- |
| Policyholder | `user` | Accept their invitation; see their policies; report, resume, and track their claims; supply evidence; reply to requests; request withdrawal |
| Agent | `agent` | Invite/enroll policyholders in permitted organizations; manage assigned claims; request evidence; publish updates; assist filing with attribution |
| Claims manager | `head_agent` | Triage, assign, reassign, review outcomes, manage escalations, and monitor work within permitted organizations |
| Platform administrator | `admin` | Manage organizations, staff memberships, access, and prototype configuration; use explicit, audited permissions for claim operations |

Four roles are sufficient for the prototype. A surveyor/assessor, insurer user, finance user, support user, or auditor does not yet need a separate login. Store an external assessor/contact/reference where required and let the manager record a manual or simulated update. “Surveyor dispatched” must not imply that the portal actually dispatched anyone.

The invitation authority should be explicit: agents and managers can invite policyholders within their organization; platform administrators provision staff. A policyholder invitation must never be able to promote someone to a staff role. The permission map, page access, server actions, and component behavior should all implement the same policy. Currently they diverge: for example, agents have customer-read permission but the Customers page redirects them, while admin status editing is permitted but admin note/progress editing is not.

Staff roles are currently global even when a person belongs to several organizations. For this prototype, keep each staff member's role consistent across those organizations. If someone later needs to be a manager at one insurer and an agent at another, use membership-level roles; adding another global role will not solve that problem.

**The invitation journey the prototype should demonstrate**

1. The agent selects their organization and associates the policyholder with a manually recorded or clearly marked demo Motor/Burglary policy. Normalize the email and validate/store the contact number.
2. The portal creates a pending enrollment and a single-purpose invitation, with creator, organization, allowed policy, expiry, and delivery state. It does not pre-create an unusable password account.
3. The recipient sees who invited them, the organization, a masked policy reference, and valid/expired/used/revoked link state before entering personal information.
4. A new recipient creates their own credentials and proves email ownership. An existing recipient signs in and explicitly accepts. Preserve the invitation through sign-in and verification.
5. Acceptance associates the correct identity and policy once, records the accepted account and time, and gives the policyholder a clear “Report an incident” action.
6. The agent can see pending/accepted/expired/delivery-failed invitations and resend or revoke an unused invitation. Resend invalidates the previous link. Existing accounts and expired invitations must be normal supported cases.

**How the two forms should improve**

Both forms should begin with a short first report: policy/insured asset, incident or discovery date, approximate time if necessary, location, a concise description, contact details, and available evidence. Show the incident-report reference immediately. Optional details and later evidence should not prevent that acknowledgment. A saved draft is different from a submitted first report; display both states clearly.

- **Motor:** confirm or prefill the insured vehicle; ask accident/theft/other damage first; capture driver details only when relevant. Ask about injuries and third parties explicitly and allow more than one vehicle/person when needed. Include police-report availability, witnesses, current vehicle location/drivability, and repair estimate availability as follow-up information. Provide appropriate immediate assistance guidance without making insurer-specific promises.
- **Burglary:** capture event/discovery timing, residential/business premises, entry circumstances, damaged premises, alarm/security details, and police-report availability. Hide alarm-active questions when no alarm exists. Let the loss inventory contain quantity, identifying details, approximate purchase date, estimated loss, and evidence linked to each item. Permit receipts, valuations, or alternative ownership evidence as alternatives. Make stock records relevant only for business premises.
- **Shared interaction:** autosave and resume, a visible saved timestamp, an unsaved-exit warning, policy context on every step, a review/edit screen, a recorded accuracy declaration and privacy acknowledgment, and a receipt with “View claim” and “Add documents” actions. Remove registration friction such as a profile photo from the critical onboarding journey.
- **Validation and accessibility:** associate each label with its control, announce errors, move focus to the first invalid field, name icon-only step/remove/download buttons, and make upload available by keyboard. The current drop zone is a clickable `div` with a hidden input, and claim field labels generally lack control associations. Use meaningful step labels on mobile and usable numeric/date keyboards. Validate final forms as a whole and route errors to the relevant step.
- **Poor connections:** retain the claim ID and entered data through failed requests, show progress for each file, and retry individual uploads. Explain when a locally selected file must be selected again after refresh; do not claim files are saved until storage confirms them. A full offline application is not required for the first prototype.

**The complete portal experience**

For policyholders, the dashboard should prioritize outstanding actions, then current status, recent updates, their agent/contact fallback, and their policy. Each claim should have its own authorized detail URL containing the original report, later amendments, categorized documents, requests and replies, public timeline, and receipt. New reports should warn about a possible duplicate incident without blocking legitimate separate incidents. Requesting a correction or withdrawal should preserve the submitted history.

For agents, provide a searchable/filterable assigned queue and a policyholder invitation list. A claim workspace should support evidence review, a structured request for missing information, public replies, internal notes, manual assessment information, and a clear next task. Requests need an owner, requested document/detail, due date where appropriate, and resolved state. Agents must retain onboarding access when their queue is empty, but a person with no organization must see a setup state rather than mock success.

For managers, provide an organization queue with claim selection, correct assignment/reassignment, overdue/unassigned work, workload, and outcome review. Record assignment history and prevent concurrent assignments from silently overwriting each other. Removing a staff membership must flag or reassign their open work. Counts and elapsed-time indicators must use actual stored evidence and have honest empty states.

For administrators, complete staff access management: provisioning, suspension/reinstatement, membership removal, session revocation where appropriate, and an audit of access changes. Keep insurer organizations distinct from the third-party portal operator. Retain the existing visual system while giving each role navigation appropriate to its job.

Across the portal, keep an append-only event history for submission, assignment, evidence requests, status changes, outcome reasons, amendments, and withdrawal. Store actor, time, reason, and previous/new values where relevant. Record the policy/form version used at submission. Default to authenticated private documents and minimum necessary personal data, with a clear explanation of what the portal operator collects and how people request help or correction. Use synthetic identities and documents for demonstrations.

Insurer integration remains deferred. Manual export of a reviewed claim package and a manually entered external reference can demonstrate handoff without building an integration. Label external submission, approval, dispatch, and settlement as pending, manual, or simulated according to the evidence available. The portal must not claim that an insurer received a claim or paid money merely because someone checked a progress step.

| 4. Follow-up and staff workflow | Claim detail pages, evidence requests/replies, public/internal timeline separation, inbox/read state, real reassignment, allowed status transitions, withdrawal, honest outcomes | An agent requests evidence; the policyholder sees and resolves the request; the manager reassigns a claim and it persists; status, progress, notification, and outcome agree |

Avoid expanding the policy catalog or introducing more roles during these phases. Search, filters, and a simple export belong in completion work; advanced fraud scoring, real payments, automated coverage decisions, and insurer adapters can wait.

**What should be tested before calling the prototype complete**

- New invited account, existing account, wrong email, expired/revoked/used token, resend, failed email delivery, and two simultaneous acceptance attempts.
- Policyholder ownership, assigned versus unassigned agent, wrong organization, manager scope, and staff membership removal on every claim read/write/upload/download path.
- Both incident journeys with unknown timing, no police report yet, unavailable documents, receipt alternatives, contradictory answers, invalid money, and future/invalid dates.
- Refresh and session interruption, duplicate submission, a failure midway through file upload, a missing storage object, unsupported/oversized files, and upload retry against the existing claim.
- Evidence request and response, rejection reason, withdrawal, reopening, manager reassignment, notifications, and consistent status/progress.
- Organization switching, rapid claim selection, zero-claim dashboards, keyboard upload, screen-reader labels/errors, and mobile completion.

Add focused automated tests for authorization, invitation consumption, validation, submission idempotency, and state transitions, plus a small end-to-end demo suite. Keep test data and test services isolated from real policyholders. No test runner or project test suite is currently configured.
